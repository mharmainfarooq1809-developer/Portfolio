About

I build the systems businesses run on behind the login screen.

Most of my work never faces the public internet — it faces an admin logging in every morning to check shipments, invoices, or stock. That's the software I build: dashboards and portals that hold up under daily, repeated use.

I work primarily in PHP and Laravel, with MySQL underneath and a JavaScript layer that keeps interfaces fast and responsive. Every system I ship is designed around one question: what does the person using this every day actually need to see?

Based in Pakistan, working with clients wherever the project takes me — logistics, retail, and internal operations tooling are where I've spent the most time.

Featured Case Study

Union Enterprises

An import & export logistics management system built to replace spreadsheet-based tracking with a single operational platform.

Import & Export Logistics Platform

LaravelMySQLREST APIRole-Based Access

Problem

Shipment status, invoices, and client documents were spread across spreadsheets and email threads, with no single source of truth for either the internal team or clients.

Research

Mapped the daily workflow of the operations team and the information clients repeatedly asked for, to decide what belonged in the admin dashboard versus the client portal.

Solution

A two-sided platform: an admin dashboard for internal operations, and a client portal for shipment visibility — connected by one database and a consistent permission model.

Architecture

Laravel MVC structure with role-based middleware separating admin and client access, REST endpoints powering dynamic dashboard views.

Database Design

Normalized MySQL schema linking shipments, invoices, and documents to clients — built to support reporting without duplicating data.

Results

Replaced manual status updates with live tracking and centralized invoicing and document management in one place.

Development Philosophy

Start from the daily user

The person who opens this every morning defines the interface — not the feature list.

Design the schema first

A clear database structure prevents most of the problems that show up later as "bugs."

Roles before features

Who can see and do what is decided before a single screen is built, not patched in afterward.

Ship what holds up

Software that survives daily, repeated use — not just a demo that looks good once.
